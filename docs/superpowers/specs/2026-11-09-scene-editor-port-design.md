# 設計書: minirobo-editor 全面移植とシーン実行（閉ループ・同期・退避）

- 日付: 2026-11-09
- 状態: 承認済み（2026-11-09）
- 対象: `web-controller`（Next.js 14 / TypeScript / CJS(tsx)）、`firmware/esp32_rc_car`（変更なしの方針）
- 移植元: https://github.com/Takumi-Araki-92/minirobo-editor （Robot Scene Studio r13、コミット `e937be4`）。作者から全面移植の承諾済み。

## 1. 目的と成功条件

フリートの自動ルート機能を、時間軸エディターで作った「シーン」で駆動できるようにする。

**成功条件（利用者の言葉）**: エディタで作ったルート通りに複数台の実機が予定どおり動き、ARマーカーによる位置補正を行ってぶつからずに、エディタで決めた要素ごとに同期して動く。

完了の判定（受入）:
1. エディターで作成した、移動・旋回を含むシーンを、4台の実機で最後まで実行できる。
2. 各動作バーの完了を、測位の値で判定する（位置20mm以内・向き5°以内が0.3秒続くこと）。
3. 実行中に、安全半径60mmの円どうしが重なる接触が0回である。
4. 人物・扉・汚れなどの演出が、実機の進行と同じ時刻（進行時計）で表示される。
5. 8台構成でも、シミュレーター上で上記1〜4を満たす。

## 2. 非目標・アンチゴール

- 非目標: 実在の扉・EV・PLC・空調との接続。人物は描画だけで、実在しない。
- 非目標: ファームウェアの変更。既存の `drive`（a〜eと左右PWM）だけで制御する。
- 非目標: 移植元リポジトリとの継続的な同期。移植後は独立して進める。
- 非目標: 配布用の仕組み（`start.ps1`、Node.jsの自動導入、ZIP作成）、外部向けの `/api/fleet` HTTP、`scene-scenario-draft`（百分率座標）の出力。
- アンチゴール: 予定の時刻どおりに見えるが、実機が予定位置にいない状態で次へ進むこと。失敗やタイムアウトを成功扱いにすること。
- アンチゴール: 測位が受入基準に達していない状態で、閉ループ走行を有効にすること。

## 3. 前提・制約

| 項目 | 内容 |
|---|---|
| 走行面 | 50インチ・16:9の画面（有効表示 1106.93×622.65mm。`data/field.json` の既定値） |
| 実機 | 上から見た外形は60〜80mm角で、機体ごとに異なる。エンコーダー・IMUなし。L298Nを左右PWMで駆動 |
| 台数 | 最大8台。通常は4台 |
| 測位 | 俯瞰カメラ＋ArUco（`robot_pose/v3`、1600×900の比率座標）。Hubでmmへ換算（[poseStore.ts](../../../web-controller/fleet/poseStore.ts)） |
| 測位の受入基準 | 既存の計画書の8節に従う（静止時の標準偏差3mm以下、絶対誤差15mm以下など） |
| 閉ループの着手条件 | PR2の実機計測が受入基準を満たした場合のみ（既存の方針を維持） |
| 技術 | Next.js 14、React 18、TypeScript、Hubは `tsx`（CJS）。テストは `tsx --test`。トップレベルawaitは使わない |
| フェイルセーフ | ESP32は1.5秒間命令を受けないと停止する。Hubは800ms周期で命令を送り続ける |

```text

    units.ts             mm・角度・比率座標(1600x900)の変換
    grid.ts              20mmの保存マス、描画グリッド（20mmの整数倍）、半端の扱い
    floorPlan.ts         部屋・廊下・床材・家具・壁・扉・ゲート・EV・充電スペース
    navigation.ts        通行の可否・壁線分・開口・障害物（外部連携用の派生データ）
    safety.ts            半径60mmの円による壁・家具・領域・軌跡の判定
    doors.ts             解錠期間・通過・開度（描画用。実在の扉は制御しない）
    model.ts             プロジェクト・マップ・行・アクションの型、検証、保存用の整形
    timedPlan.ts         固定時間軸の計画（compilePlan / samplePlan）

    scenarioLibrary.ts   16本のシナリオ（mm・半径60mmで作り直す）
    legacyImport.ts      robot-scene v2〜v5 → 本形式への一度だけの変換（D11）
  fleet/
    sceneStore.ts        シーンの保存（data/scenes/）と編集履歴（data/scene-history/）
    sceneRunner.ts       進行時計・同期の待ち合わせ・バーの割り当て（D2〜D4）
    motionController.ts  1台ごとの閉ループ（位置→a〜e＋左右PWM）
    trafficManager.ts    接近の予測・優先の決定・退避経路（D14, D15）
    anomalyPolicy.ts     見失い・引っかかりの判定と状態遷移（D12, D13）
    calibration.ts       走行特性の校正（既存の計画書のPR3 1項）
```

- 予定計算・安全判定・扉の処理は `scene/` に置き、ブラウザーとHubで共有する。エディターのプレビューと実行時の判定がずれないようにするため。
- 既存の [routeEngine.ts](../../../web-controller/fleet/routeEngine.ts) は残す（D18）。Hubでシーン実行と排他にし、一方の実行中は、もう一方の開始を拒否する。

## 7. 座標・グリッド・データ形式

- 世界座標の単位はmmで、範囲は0≦x≦1100、0≦y≦620。測位の比率座標とは `units.ts` だけで変換する（x_mm = x / 1600 × widthMm、y_mm = y / 900 × heightMm）。
- 保存するマス: 55×31。マス番号は**左下を起点**とし、行優先で並べる。移植元の左上起点は採用しない。
- 描画グリッド: `gridMm ∈ {20, 40, 60, 80, 100}`。マップごとに保存する。粗いグリッドで描くと、20mmのマスを(gridMm/20)²個まとめて塗る。
- 新しい保存形式は `fleet-scene/v1`。移植元の `robot-scene/v2〜v5` は `legacyImport.ts` だけが読む。変換方法: 比率座標 → mm（×1106.93/1600、×622.65/900）→ 20mmのマスへ丸める（各マスの中心が元の領域に含まれれば塗る）。そのうえで全アクションの通行判定をやり直し、通れない行を一覧にする。
- ロボットの行は `robotId` を持ち、`fleet.json` のロボット定義を参照する。マーカーIDは `robotStore` から引く。
- `fleet.json` の拡張: 外形の `footprintMm {w, d}` と、固定順位の `priority` を任意項目として追加する。

## 8. 実行モデル

### 8.1 進行時計
- 状態: `idle → arming → running ⇄ waiting → finished / aborted`。どの状態からでも `halted`（全台停止）へ移る。`halted` から操作者が「再開」か「中止」を選ぶ。操作者による一時停止もこの `halted` で表す。
- 実行前の確認（arming）: 次をすべて満たすときだけ開始できる。基準マーカーが3枚以上見えている（`extrinsics_ok`）、対象の全台が追跡中、校正済み、全台が初期位置の到着判定を満たす、測位が正常。
- `running` の間、進行時計 `t` は実時間で進む。バー `[start, end]` の終了時刻 `end` に達したとき、担当する機体が到着判定を満たしていなければ `t = end` で止めて `waiting` にする。全台・全演出がここで待つ。
- 先に終わった機体は、次のバーの開始時刻まで、その場で停止して待つ（停止命令 `e`）。
- 演出は `samplePlan(plan, t)` で描く。`t` が止まれば演出も止まる。

### 8.2 1台ごとの動き（motionController）
- 旋回バー: その場で回る（`c` か `d`）。向きの誤差に応じてPWMを決める。
- 移動バー: 目標方向を向いてから前進（`a`）。進路のずれに応じて左右のPWMに差をつけて補正する。予定の速度は「距離÷バーの長さ」から求め、校正値の範囲内に制限する。
- 待機バー・バーのない時間: 停止。
- 命令は800ms以内の周期で送り直す（フェイルセーフの維持）。

### 8.3 接近時の調停（trafficManager）
- 各機体について、これから2秒間の予定軌跡（計画と現在位置から算出）を予測する。2台の中心間距離が120mm（半径60mm×2）＋予測の余裕を下回りそうになったら、調停を始める。
- 退避できるかの判定: 優先機の残りの経路に、幅120mmと余裕を足した帯を作る。帯の外で、壁・家具・他の機体・見失った機体の範囲と重ならない地点を、20mmのマスの上で探索する。その地点までの経路も通行判定にかける。
- 優先の決定はD15の順。退避中は「完了待ち」の扱いで進行時計を止め、優先機だけを動かす。
- 優先機が通過したら、退避した機体は離れた地点へ戻り、元の動作を再開する。

### 8.4 異常時（anomalyPolicy）
- 見失い: 測位の値が `POSE_STALE_MS` を超えて古くなったら、見失ったと判定する（D12）。
- 見失い後の自動再開（D19）: 次をすべて満たす状態が1秒続いたら再開する。対象の全台が追跡中、基準マーカーが3枚以上見えている、見失っていた機体の位置が停止前の位置から安全半径（60mm）以内にある。位置が大きくずれている場合（人が動かしたなど）は自動再開せず、操作者の「再開」を待つ。再開の前に、各機体は予定位置とのずれを通常の閉ループで補正する。
- 引っかかり: 前進を指示しているのに、2秒で10mm未満しか進まない（既存の計画書の値）。再試行は1回まで（D13）。
- 領域外に出る、測位が切断する、基準マーカーが2枚以下になる（`extrinsics_ok=false`、全台の位置が無効になる）: 全台停止。基準マーカーは3枚でも測位できる実装（[geometry.ts](../../../web-controller/localization/geometry.ts) は3枚のとき各マーカーの4隅で12点を使う）なので、闉ループも続ける。既存の計画書の「4枚そろったときだけ闉ループ、3枚は表示のみ」は置き換える（D16）。

### 8.5 走行面への展示表示（D20）
- `/exhibit` をHubのPCから50インチ画面へ全画面で表示する。画面の有効表示域（1106.93×622.65mm）を画面の解像度へ等倍率で対応づけ、左下を世界座標の原点とする。描ける範囲（1100×620mm）の外側は黒で塗る。
- 画面上の位置と実際の位置の一致を確かめるため、展示表示に「位置合わせ表示」を設ける。20mm格子と既知の座標の十字を映し、そこに置いた実機の測位値との差を表示する。
- 実機は実物が画面上にあるため、ロボットの本体は描かない（移植元の展示モードと同じ）。部屋の作業表示など、ロボットに付随する表示は測位の位置に合わせて描く。
- マーカー検出への影響を抑えるため、四隅の基準マーカーの周囲には何も描かない。白黒の正方形が並ぶ模様（マーカーと誤認しうるもの）は演出に使わない。
- 展示表示を映した状態での検出率・精度は、G（PR2の実機計測）で「画面が黒」と「展示表示中」の両方を測る。展示表示中に基準を満たさない場合は、表示の輝度・配色を調整する。

## 10. テスト方針

- `scene/` は純粋な関数で書き、`tsx --test` で単体テストする。移植元のテストを対応表付きで移す。
- `sceneRunner`・`trafficManager` は時刻と送信先を外から渡せる作りにし、合成した測位を入力に、状態遷移を決定的にテストする。
- UIはPlaywrightで確認する（既存の手順: EdgeのCDP、両テーマ、幅320/768/1280px）。
- 回帰の確認として、既存の `test:fleet`、`test:localization`、`test:appearance` を毎回実行する。
