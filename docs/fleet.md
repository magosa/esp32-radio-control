# Fleet運用と通信

## 画面のURL

| URL | 内容 |
| --- | --- |
| `/control` | 手動走行（個別／複数制御）・表情・カメラ撮影／ライブ（旧 `/fleet`） |
| `/field` | フロアマップ（ロボットの位置・向き・軌跡・追跡状態） |
| `/robots` | ロボット構成（カメラの紐付け、測位マーカーID・高さ、優先順位・外形） |
| `/scenes` | シーンエディター（マップ作成・時間軸編集・テストシナリオ集・展示操作） |
| `/run` | 実行（シーン実行の閉ループ制御・進行時計・退避、および測位なしの簡易ルート） |
| `/exhibit` | 50インチ走行面用の全画面展示表示（位置合わせ表示 `?align=1` を含む） |
| `/localizer` | 俯瞰カメラの開始・停止、検出結果、領域設定、CSV記録 |
| `/settings` | 表示設定（旧 `/fleet/settings`） |
| `/direct/bluetooth` | Bluetooth直接操作（旧 `/bluetooth`） |

`/`、`/fleet`、`/fleet/settings`、`/bluetooth`、`/api/fleet/routes` は新URLへ一時リダイレクトします。
ESP32は従来どおり `/ws/device`、ブラウザーは `/ws/client` に接続します（ファームウェア固定のため変更しません）。

### シーンのテストシナリオ

「マップを追加」では、既存マップの部屋・廊下・壁・家具・扉をサムネイルで確認してコピー元を選べます。コピーするのは配置のみで、ロボット・人・シーケンスは含みません。「新しくマップを描く」を選んで「追加」すると、新しいマップのタブを作成・選択し、そのマップの編集画面を自動で開きます。編集をキャンセルしても追加済みの白紙マップは残り、マップの追加自体は通常の「元に戻す」で取り消せます。

「テストシナリオ集」から選び、「マップとして追加」で新しいタブへ追加します。16本は移植元の動作をmm・安全半径60mmへ再構築したもので、日常運用の3役割、通路・扉の優先通行、退室後の部分清掃などを含みます。検知・判断・建物連携・遠隔操作は固定の模擬ストーリーであり、実設備には接続しません。

エディターのステージと全画面プレビューにはロボットを表示します。実機を置く `/exhibit` では引き続きロボット本体を描きません。テンプレート更新は保存済みマップを自動変更しないため、旧シナリオを使っていた場合はシナリオ集から追加し直してください。追加は元に戻す・やり直し・履歴保存の対象です。

### シーンエディターの実装境界

マップ編集の家具「植物」は、ドラッグした範囲の幅・高さに合わせた植栽として表示します。自動ドアは壁付近のカーソル位置に配置候補をハイライトし、クリックで確定します。フラッパーゲートは床上に独立して配置し、新規配置時に扉の長さ方向へドラッグすると、入口幅が140〜240mmの範囲・20mm単位で変わります。ドラッグ中はプレビューと幅の表示を更新し、離したときに1回の編集として確定します。短いドラッグは140mm、長いドラッグは240mmに吸着し、配置済みゲートの幅は変更しません。クリックだけの場合は選択中の入口幅を使います。新規ゲートの側枠の標準奥行きは20mmで、必要なら奥行き・入口の向きを指定できます。既存ゲートの寸法は自動変更しません。設備の重なりやマップ外など、設置できない場合は理由を表示します。Escapeやマップ外でのリリースではゲートのドラッグを取り消します。自動ドアはドラッグだけでは設置されず、どちらの設備も適用前の取り消し・やり直し・キャンセルに対応します。

部屋の描画時に自動生成される壁は、短い壁の集まりでも部屋の連続した外周として自動ドアの候補を判定します。壁の内側・外側のどちらからでも配置でき、表示と経路判定の双方でドア幅分の開口を確保します。

フラッパーゲートは床上への独立設置と側枠を維持し、自動ドアと同じ両開きのスライド扉として表示します。扉部分は半透明の青みがかったガラスと光の反射で表現します。扉は回転せず、中央から開口に沿って両側へ平行移動し、枠に入った部分は隠れて収納されます。枠の外側には突き出さず、全開時は扉が完全に収納されて通行口を空けます。縦向きの設備では上下へスライドします。

右側の「行の管理」では、配置済みの対象設備を選び、「＋ 自動ドア」「＋ フラッパーゲート」で設備ごとの専用行を追加できます。同じ開口は複数セルで構成されていても1つの設備として扱い、専用行は1本だけ追加できます。追加時の一括設定、または設備行の選択後に右側の「＋ 開閉指示」から「開始（秒）」「終了（秒）」を指定します。開始時刻から0.6秒で開き、終了時刻から0.6秒で閉じます。開閉は指示の時刻に連動し、シークしても同じ開度になります。短い指示はその時点の開度から同じ速度で閉じ、連続する指示は開放を維持します。人やロボットがいなくても動作し、終了時に通過中なら安全に抜けるまで開放を保持してから閉じます。最後の閉鎖が完了するまで再生時間を確保します。開始は0以上、終了は開始より0.1秒以上後かつ86400秒以内です。

開閉指示は時間軸の移動・長さ変更、ダブルクリックによる再編集、除外・固定、元に戻す・やり直し、保存・再読み込みに対応します。使用中の設備やその開口を支える壁は、行・指示の参照を残したまま削除できません。領域の塗り直しでも、参照先が失われる変更は理由を表示して拒否します。保存形式は既存の `fleet-scene/v1` を維持し、設備行は `kind: "door"` と `doorId`、開放時間帯は `type: "door-open"` と `position` / `runSeconds` に保存します。従来の部屋行の「解錠」は、解錠時間内に接近へ反応する仕様を維持します。設備の開閉はシーン上の模擬動作であり、実設備への通信は行いません。

右側の「＋ ロボット」「＋ 人」は、行の追加後に初期位置のダイアログを自動で開きます。初期位置はダイアログ内のマーカーをドラッグし、「適用」で確定するとシーケンス一括設定に進みます。人の追加時は人数（1〜1000の整数）も指定でき、位置と人数をまとめて確定します。人は頭と肩のシンプルなアイコンを指定人数分並べます。数字だけの代用や表示人数の省略は行いません。大人数では配置間隔とアイコンを縮小して地図内に収め、1つの行・経路を共有するグループとして動きます。初期配置・移動前後のプレビュー・再生で同じ描画を使います。

ロボット・人の初期配置では「表示開始（秒）」にシーケンス上の絶対時刻を入力します。0 は最初から表示し、省略された既存データも0として扱います。右側のマップにはその時刻の他のロボット・人・画面表示・扉などを表示し、重複判定も同じ時刻の位置で行います（人同士の重複許可は従来どおり）。初期位置・人数・表示開始を「適用」でまとめて保存し、キャンセルでは変更しません。表示開始前はステージに描画せず、狭い廊下の占有や接触予測も表示開始以降だけを対象にします。新しい動作は表示開始以降に追加し、それより前に置いた動作は明示的な計画エラーになります。一括設定の「初期位置をマップで配置」から表示開始も再編集できます。

「＋ 画面表示」は表示位置と内容のダイアログを開きます。「表示項目」でテキスト・案内カード・サインを選び、言葉を入力すると、実際と同じ描画でマップ上に即時プレビューします。表示をドラッグし、「適用」で位置と内容を保存してシーケンス一括設定に進みます。キャンセル時は表示動作を作成しません。右側の「選択した行・動作」と「＋ 部屋」は表示せず、人の新規動作にも「＋ 表示」は出しません。保存済みの人の表示動作は引き続き再生・編集できます。部屋のシーケンスは領域の右クリックから設定できます。

「シーケンスを一括設定」や動作編集では、プレビューの「移動後」・表示位置を直接ドラッグして変更します。回転はロボットの周囲にある丸いハンドルをドラッグし、向きを指定します。移動先・回転指定用の別ダイアログや「マップで指定」ボタンはありません。ドラッグ中は保存せず、編集画面上部の「適用」で一括確定し、キャンセルでは破棄できます。ドラッグ中の Escape はそのドラッグだけを取り消します。カーソルへの自動追従・空白クリックによる位置変更・位置座標の直接入力は行いません。領域を選ぶ操作は引き続き部屋・廊下のクリックです。

右側の「設定」パネルと「選択中と同種の行を追加」ボタンは表示しません。名称・色・人数・ロボットの情報・初期位置はシーケンス一括設定で再編集できます。扉の確認モードは「マップを編集」のダイアログに移し、適用・キャンセル・元に戻すに対応します。左右のパネルはステージと同じ共通の透過ガラスカードを使います。

時間軸の「シーケンスを全画面表示」で、シーケンスの編集領域を画面いっぱいに広げられます。「元の表示に戻す」または Escape で通常表示に戻ります。表示の切り替えでシーケンスの内容やズームは変更しません。従来の「全体表示」は、時間方向を収めるズーム操作として残しています。

人の動作バーやステージ上の人物をダブルクリックした場合もシーケンス一括設定を開き、人数を変更できます。人数を変更すると作業コピーのプレビューへ即時反映し、「適用」で保存、「キャンセル」で破棄します。グループ内のどの人物を右クリックしても、その行の操作メニューが開きます。

時間軸の行名や各行の空白部分をダブルクリック（空白部分はダブルタップにも対応）すると、動作を追加せず既存のシーケンス一括設定を開きます。左のライブラリでも項目のダブルクリックで開けます。ステージ・時間軸・ライブラリのオブジェクトを右クリックすると「シーケンス一括設定」「削除」を選べます。削除は確認後に実行し、元に戻せます。固定中の行は編集・削除できず、他の行・動作から参照される領域や最後の領域も削除できません。部屋に対応する行がない場合は一括設定の作業コピーを開き、「適用」時だけ行を作成します。

ステージに「設定どおりに再生できない動作」が表示された場合は、家具・壁との接触、狭い廊下での通行重複、廊下を塞ぐ待機ロボットなどの停止理由を確認してください。一括設定でも編集対象の行の計画を検証し、実行できない設定は適用しません。待機位置・退出先・動作時刻を修正するか、不要な行を削除して解消します。安全判定を無効化したり、保存済みシナリオを自動修正したりはしません。

- ページは表示・レイアウトを担当し、選択・編集コマンド・ステージ操作・ショートカットは `useSceneEditor` にまとめています。
- ステージ・時間軸・ステータスは `sceneAnalysis` の計画と最終解析結果を共有します。キャッシュはマップのオブジェクト参照がキーのため、編集時は既存の編集関数で新しいマップを返し、元のマップを直接変更しないでください。
- 動作編集とシーケンス編集のモーダル・未適用変更の確認は `EditorShell` が担当します。
- シナリオの個別ストーリーは `scene/scenarioStories.ts`、領域・移動・扉・演出の組み立てと終了処理は `scene/scenarioStoryBuilder.ts` が担当します。保存形式や既存シナリオの自動更新方針は変更していません。

## ロボット構成

`deviceId` は物理ESP32の識別子、`robotId` は論理ロボットの識別子です。
初回接続した走行デバイスから `robot-<deviceId>` を自動作成します。
1ロボットにつき走行＋LCD機1台、任意のカメラ1台を割り当てます。
同じカメラを複数ロボットへ同時には割り当てられません。
複数制御のチェック選択は一時的な操作対象で、ロボット構成とは別です。

1. 走行機とカメラ機を同じHubへ接続します。
2. `/robots` を開き、対象ロボットの「カメラの紐付け」でカメラを選択します。
3. 「保存しました」を確認します。撮影・ライブは `/control` でロボットを個別選択し、「カメラ」から操作します。
4. 別のロボットに移す場合は、元のロボットで「未割当」に戻してから割り当てます。

未接続の登録済みデバイスも再起動後に表示されます。カメラ未接続時は撮影・配信操作だけが
無効になり、走行可能条件は変えません。走行機の切断は自動ルートを停止します。
デバイスの再接続は手動モード・停止からやり直します。

## 保存と復旧

標準の保存先は `web-controller/data/fleet.json`。`FLEET_DATA_DIR` にディレクトリを指定して
変更できます。パスはHub起動プロセスの作業ディレクトリ基準なので、絶対パスを推奨します。
ルートのnpmコマンドは `web-controller` を作業ディレクトリとして起動します。

- バージョン1のJSONにデバイス情報とロボット構成（カメラ割当・測位マーカーID・マーカー高さ）のみ保存します。
  マーカー項目がない旧ファイルは、読み込み時に「未割当・高さ 90mm」で補います。
- 俯瞰カメラの設定（カメラ高さ・領域寸法・基準黒部）は同じディレクトリの `field.json` に保存します。
- 接続状態、走行モード、映像、実行中ルートは復元しません。
- 一時ファイルへの書き込み後に置換します。保存できなければメモリ上の割当も更新しません。
- 不正な保存ファイルは自動で上書きせず、Hub起動を失敗させます。
- 1つの保存先にはHubを1プロセスだけ起動してください。共有ストレージの多重書き込みには非対応です。
- バックアップ・復元はHubを停止してから実施します。移設先PCにもファイルを移してください。
- 保存先はPCローカルです。Git pushだけでは別PCの割当は移りません。
- 削除・物理走行機交換の画面操作は未実装です。必要時はHub停止中にバックアップを取り、
  保存JSONの整合性を保ってメンテナンスしてください。cameraDeviceIdを解除してからdeviceを除去します。

`FLEET_DATA_DIR` を標準以外のリポジトリ内パスへ変更した場合、そのパスもGit除外してください。

## 通信契約

ESP32は `/ws/device`、ブラウザーは `/ws/client` に接続します。
型定義は [protocol.ts](../web-controller/fleet/protocol.ts) です。

```json
{"type":"hello","deviceId":"rc-example","name":"Robot","fw":"4.1.0","capabilities":["drive","display"]}
```

```json
{"type":"hello","deviceId":"cam-example","name":"Camera","fw":"camera-1.0.0","capabilities":["camera"]}
```

`capabilities` 未指定の旧helloは `drive`＋`display` として受け入れます。
旧来の走行コマンド・テレメトリ・表情・レイアウト形式は維持します。
旧一体型カメラFWはカメラ能力を宣言しないため、映像送信元としては扱いません。

| 機能 | メッセージ |
| --- | --- |
| 走行 | Hub→`drive`、デバイス→`telemetry` |
| 表示 | Hub→`setExpression`／`setDisplayLayout` |
| 撮影 | Hub→`captureImage`、カメラ→`imageFrame`（JPEG Base64） |
| ライブ | Hub→`streamStart`／`streamStop`。配信中のカメラだけに`ping` |
| カメラ生存確認 | カメラ→`heartbeat`。モーター用telemetryは不要 |
| 構成編集 | UI→`assignCamera`（requestId／robotId／cameraDeviceId）、`assignMarker`（markerId／markerHeightMm）、`setFieldConfig`。Hub→`operationResult` |
| 測位 | 俯瞰カメラ（`/ws/localizer`）→`localizerHello`／`poseFrame`／`localizerStatus`、Hub→UIは約10Hzの`poseState` |
| 状態配信 | `fleetState`: 従来の走行機一覧`vehicles`＋物理一覧`devices`＋構成`robots` |

Hubは接続socketのdeviceIdを固定し、他のdeviceIdを名乗る後続メッセージを拒否します。
能力とオンライン状態に基づき送信先を制限します。名前やIDは認証情報ではありません。
信頼できるLANのみで使用し、ポート転送・不特定端末の接続は許可しないでください。

カメラは1秒ごとにheartbeat、Hubは5秒更新がなければ未接続判定します。
XIAOはHubから5秒受信がなければ配信を止めます。再接続時に配信を自動再開しません。
最後の閲覧クライアントが閉じたとき・割当変更時にも配信を止めます。
配信の開始／停止は全閲覧者共通です。複数閲覧者が同じカメラを操作すると相互に停止できます。
フレームは保存せず、遅いブラウザーにはフレームを間引きます。
Hubの受信上限600,000bytes、JPEG Base64上限512,000文字、XIAOのJPEG上限120KiBです。

走行FWは従来どおり1.5秒の受信途絶で停止します。Hubは走行機へ生存確認pingを送りません。
手動操作の200ms再送と自動ルートの800ms再送は、停止・通信断の安全機構とは独立です。
停止指示は自動モードでも届き、関連する自動ルートの再送・予約を取り消します。

## 測位（俯瞰カメラとARUCOマーカー）

計画と設計は [ar-localizer-plan.md](ar-localizer-plan.md) を参照してください。現在は表示・監視・追跡状態の提供までで、走行制御には使いません。

- マーカー: `DICT_4X4_50`、基準ID40（左上）・41（右上）・42（右下）・43（左下）、ロボットID0〜7（最大8台）。
  ロボット上ではマーカー画像の右方向をロボット前方に合わせます。黒部寸法は基準が設定値（初期33mm）、ロボットが40mmです。
- 手順: 俯瞰USBカメラをHub実行PCへ接続 → `/robots` でマーカーIDとマーカー高さを設定 →
  `/localizer` で領域設定を確認して保存 → カメラを選んで「開始」 → `/field` で確認。
- 測位は**Hub実行PCのlocalhostで開いたページ**からのみ開始できます。検出ループはシェルで常駐し、同じタブで画面を移動しても続きます。
  ウィンドウが背面・最小化されると検出が遅れる・止まることがあるため、警告を表示します。
- Hubは`/ws/localizer`を、loopbackからの接続で、かつOriginがこのHubのlocalhost系のときだけ受け付けます。
  `FLEET_LOCALIZER_ALLOW_REMOTE=1` で緩和できますが、偵の姿勢を送られるリスクがあるため非推奨です。
- 追跡状態: 追跡中（最新フレームで検出）／未検出（フレームは届くがマーカーなし・飛び値を棄却）／
  測位なし（フレームが0.5秒以上途絶・未接続・停止）／マーカー未割当。過去の座標は保持しません。
  500mm/sを超える飛びは棄却し、同じ場所が3フレーム連続したときだけ受理します（暫定値）。
- 基準マーカー: 検出できていない四隅のIDは、`/field` のマップで赤い四角で示し、トーストにもIDを表示します（`/localizer` も同様）。
  測位が動作していないときは検出状態が不明なので赤にしません。
- 測位接続は1つで、先着優先です。稼働中は別の接続（別タブや疑似 localizer）を拒否し（close 1013）、
  3秒間何も届かない接続だけが新しい接続に置き換わります。拒否された測位画面は数回再試行して停止し、理由を表示します。
- 座標: Hub内部はmm（原点左下、X右・Y上、向きは右0°・反時計回り正）。CSVは原本どおり`robot_pose/v3`の比率座標（1600×900）です。
- 実機の絶対精度・検出率・遅延は未検証です。受入基準は計画書の「受入基準」を参照してください。

## 実機なしの確認

別PCの運用Hubではなく、専用のローカルHubと保存先を使います。
以下はPowerShellで、それぞれ別ターミナルから実行します。

```powershell
$env:PORT = '3117'
$env:FLEET_DATA_DIR = Join-Path $env:TEMP 'esp32-fleet-demo'
npm run dev
```

```powershell
$env:FLEET_HUB_HOST = 'localhost'
$env:FLEET_HUB_PORT = '3117'
npm run sim:device -- --fleet
```

<http://localhost:3117/control> を開きます。`--fleet` は走行用2台とカメラ用1台です。
単体起動は `npm run sim:device -- <deviceId> <name> <drive|camera|legacy>` です。
俯瞰カメラなしで測位UIを確認するには、続けて `npm run sim:localizer -- --assign --drop` を実行します（現在の場合は
`FLEET_HUB_PORT` を合わせる）。`--assign` は先頭2台へマーカーID0/1を割り当て、`--drop` はマーカー1を周期的に隠します。
シミュレータを終了しHubを再起動して、割当が残り接続状態は未接続へ戻ることも確認できます。
自動テストは一時保存領域と偽socketを使用し、実機へ接続しません。

## 接続診断

ESP32とHub実行PCを同じ2.4GHz対応LANへ接続します。スマホテザリングのIPは変わるため、
Hub実行PC側でIPv4とポートを確認し、各スケッチのローカル設定を更新してください。
この開発PCのIPを無条件に転記しないでください。ゲストWi-Fiの端末間隔離と
Windowsファイアウォールも確認してください。Bluetooth直接操作はWeb Bluetooth対応の
Chrome／EdgeでlocalhostまたはHTTPSを使います。Classic BTは対応SPPクライアントで操作します。
